## 一、方法

1. 逐条抽取旧站的技术结论，按主题归并为 30 条（现为 `C-001`–`C-030`）。
2. 对每条结论找**一手来源**：上游仓库的 README / Release / 提交记录优先，官方文档次之，社区实测再次之。
3. 给每条来源标注证据等级与核验日期；找不到一手来源的，降级为「项目方声明」或「推断」，并在结论上打 `needsVerification`。
4. 与旧站结论冲突时以新证据为准，旧说法进「取证纠错」。
5. 无法核实的**不删除、不补造**，保留条目并显式标注不确定。

## 五、审计中发现的、旧站没有的结构性问题

1. **同一硬件在两处维护**：旧站 `matrix` 与 `cpus/gpus` 是两套数据，已经出现「matrix 说 51 条、实际 50 条」的偏差。新版合并为单一 `HARDWARE`。
2. **规则用字符串比较**：旧引擎靠 `level === 'none'` 判断，新增型号必须改代码。新版改为判别式字段。
3. **状态语义不足**：旧版只有 5 态，无法表达「有方案但没证据」。新版补 `unverified` 与 `unknown`。
4. **没有证据字段**：旧版结论只能靠文末来源列表笼统对应。新版每条记录挂 `evidenceIds`，启动时校验引用。

## 六、已知限制与遗留

- **未做真机验证**：所有兼容性结论均来自公开资料，未在本机复现。这是本站最大的局限。
- **star 与提交时间是快照**：2026-10-29 抓取，之后会漂移；页面标注了日期但不会自动更新。

- **旧站 SVG 图未迁移**：新版用表格与结构化文本替代，信息等价但没有图示；`legacy/` 里保留了原文件。
